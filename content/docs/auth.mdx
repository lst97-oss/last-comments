Every request resolves to a provider-neutral identity, so routes and guards never depend on a specific auth SDK. Deployers pick the providers in `src/server/auth/auth.config.ts` (`providers`, first match wins); adding a provider never requires touching a route. `AUTH_PROVIDERS` in the environment overrides the file when set (per-environment sets).

`GET /api/auth-providers` reports the active providers (public, no secrets) so the sign-in UI renders the right form.

<Tabs items={["better-auth", "oidc-jwt", "header"]}>
<Tab value="better-auth">
Built-in email/password plus optional Google OAuth, with session cookies for the dashboard and widgets.

```ts
// src/server/auth/auth.config.ts
providers: ['better-auth'], // default
```

- `BETTER_AUTH_SECRET` (min 32 chars), `BETTER_AUTH_URL`, and optionally `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`. Register `http://localhost:3000/api/auth/callback/google` as the OAuth redirect URI.
- Google sign-in links to an existing account with the same email, even when that account's local email is unverified (the first admin signs up with a password, which leaves it unverified). Google's own `email_verified` claim is the ownership proof. Without this, the callback fails with `account_not_linked` and the reader returns to the site without a session. Password sign-up is closed, so nobody can pre-register a victim's address. Better Auth marks `requireLocalEmailVerified` as deprecated; re-check this setting when upgrading.
- Public password registration stays disabled; the login endpoints live under `/api/auth/*`, including the interactive reference at `/api/auth/reference`. That whole mount is only served while `better-auth` is in `providers` (chains like `['better-auth', 'oidc-jwt']` count) and answers 404 otherwise.
- On a new database, open `/create-admin-user` to create the first admin. Until an instance admin exists, the server refuses all other account creation — except the single address in `bootstrapEmail`, which may register directly (for headless deploys without the setup form).
</Tab>

<Tab value="oidc-jwt">
Bearer JWTs from an identity provider you already run — Auth0, Clerk, Keycloak, Entra ID, Supabase Auth, and others. API clients send `Authorization: Bearer <idp-token>`.

```ts
// src/server/auth/auth.config.ts
providers: ['oidc-jwt'],
```

```bash
# Endpoint identity stays in the environment:
AUTH_OIDC_JWKS_URL=https://idp.example.com/.well-known/jwks.json
AUTH_OIDC_ISSUER=https://idp.example.com/
AUTH_OIDC_AUDIENCE=last-comments
```

- Signatures verify against the cached JWKS (10-minute cache, refreshed once on key rotation); issuer and audience are pinned, `exp` is enforced with a 60-second leeway (`clockSkewSeconds`), and unsigned algorithms are rejected.
- The subject (`sub`) links to a user via the [identity mapping](#identity-mapping) below; names and avatars come from the `name` / `picture` claims when present.
- The email claim defaults to `email` (`emailClaim`). Only a verified address (`email_verified: true`) links to an existing user.

<Callout type="warn" title="Dashboard sign-in">
  `oidc-jwt` authenticates API callers holding IdP tokens. Interactive dashboard sign-in needs a cookie session: keep `better-auth` in the chain or put the dashboard behind the `header` provider.
</Callout>
</Tab>

<Tab value="header">
Identity headers from a proxy that already authenticated the user (Cloudflare Access, Authelia, Pomerium…).

```ts
// src/server/auth/auth.config.ts
providers: ['header'],
header: {
  trustProxy: true,
  proxyCidr: '10.0.0.0/8',
  userHeader: 'x-forwarded-user',
  emailHeader: 'x-forwarded-email',
  nameHeader: 'x-forwarded-name', // default shown; omit keys you don't override
},
```

<Callout type="error" title="Fail closed by default">
  Without `trustProxy: true` the headers are ignored entirely. With it, requests arriving outside `proxyCidr` are ignored too — a misconfigured proxy fails closed instead of trusting forged headers.
</Callout>
</Tab>
</Tabs>

## Identity mapping

External subjects link to the canonical user row (`external_identities`: provider + subject → user), so site memberships, votes, and comments keep joining on `user.id` no matter which provider signed the user in:

- A verified email links to the existing user with that address (same human, new provider).
- An unverified email **never merges** — it provisions a separate user, so a forged claim cannot take over an account.
- Unknown subjects auto-provision a linked user; `autoProvision: false` requires accounts to exist first.
- The first external login on a fresh instance claims the singleton instance-admin slot (restricted to `bootstrapEmail` when set); afterwards external users get zero site roles until an admin grants them.

## Service keys

Publisher keys (`lck_*`) verify before any session provider and are unaffected by the choice above — machine callers keep working when interactive login moves to OIDC or proxy SSO. Keys are issued server-side only, with permissions and site binding the client can never set.

Two comment scopes let a host server act for its visitors without exposing the key to the browser: `comments:read` loads a site's comments and `comments:write` posts and edits guest comments. A key holding them never acts as a user, and votes stay session-only. Both scopes need a key bound to one site.

## Who can comment: access and the gateway

Each site has two settings, set in the dashboard or with `PATCH /api/admin/sites/{siteKey}`.

| `access` | Anyone can read | Anyone can post and edit |
| --- | --- | --- |
| `open` (default) | yes | yes, from a registered Origin, with a verification challenge |
| `login` | yes | no: needs a signed-in session or a key |
| `private` | no: needs a session or a key | no: needs a session or a key |

`gatewayOnly` (default `false`) is the transport setting. When it is on, a request without a site-bound key is refused with `403 FORBIDDEN`, even with a registered Origin. An Origin header is set by the caller, so it proves nothing against a script or curl; the key is what proves the request came through your host.

Pick the setting that matches what your host can run:

| Host | Where a key can live | Typical setting |
| --- | --- | --- |
| No server (static site, GitHub Pages) | Nowhere: a key in browser code is public | `open` with the default widget. Turnstile and rate limits are the only protection. |
| A function or edge runtime | The function's environment | `open` plus `gatewayOnly`, with a small proxy function. |
| A full server | The application's environment | `open` plus `gatewayOnly`, with the proxy in the application. |

`login` and `private` use the comments service's own session cookie, which a browser sends only to the API's registrable domain. Use them only when the API sits on a sibling subdomain of the page (for example `comments.example.com` for `www.example.com`). They are not an option for an arbitrary static host.

A host proxy sends `x-lc-client` with a stable, per-visitor value (16 to 128 letters, digits, `-` or `_`). The service rate-limits each visitor by that value, not by the proxy's own address, which would otherwise share one budget across all visitors. Without it, a keyed call is limited per key.

## Configuration reference

Policy lives in `src/server/auth/auth.config.ts`; endpoint identity and credentials stay in `.env` (see `.env.example`).

| File key | Purpose | Default |
| --- | --- | --- |
| `providers` | Enabled providers, first match wins (`AUTH_PROVIDERS` env overrides when set) | `['better-auth']` |
| `autoProvision` | Create linked users on first external login | `true` |
| `bootstrapEmail` | Only address allowed to claim the first admin remotely | unset |
| `header.trustProxy` / `header.proxyCidr` | Enable proxy SSO / allowed proxy source | `false` / `*` |
| `header.userHeader` / `header.emailHeader` / `header.nameHeader` | Trusted header names | `x-forwarded-*` |
| `oidc.emailClaim` / `oidc.clockSkewSeconds` | Email claim name / expiry leeway | `'email'` / `60` |

| Env key | Purpose |
| --- | --- |
| `AUTH_OIDC_JWKS_URL` / `AUTH_OIDC_ISSUER` / `AUTH_OIDC_AUDIENCE` | Trusted JWT settings for `oidc-jwt` (required when enabled) |
