The repository ships a `compose.yaml` stack for local development and small self-hosted deployments. It runs PostgreSQL 18, applies both migration sets, starts the app on port 3000, and runs the plugin outbox worker.

## Requirements

- Docker Engine with Compose v2.24 or newer.
- At least 2 GB of RAM for the image build and PostgreSQL.
- A public HTTPS origin for production (the server rejects loopback origins when `NODE_ENV=production`).

## Start the stack

```bash
cp .env.example .env
# set PAYLOAD_SECRET and BETTER_AUTH_SECRET (32+ characters)
bun run stack:up
```

`stack:up` is `docker compose up -d --build --wait`. The equivalent raw commands are:

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f app
```

Open [http://localhost:3000](http://localhost:3000). The Compose file works without a `.env` file for local evaluation; the defaults are development-only secrets.

| Service | Purpose |
| --- | --- |
| `postgres` | `postgres:18-alpine`; Payload database `template_demo`, business database `business_comments` |
| `migrate` | One-shot `bun run db:migrate` + `bun run db:business:migrate`; `app` and `worker` wait for it |
| `app` | The Nitro server on `:3000`, published on `127.0.0.1:${APP_PORT}` only |
| `worker` | `bun scripts/plugin-worker.ts`, delivering the plugin outbox |
| `tunnel` | `cloudflare/cloudflared` public ingress; only with `--profile tunnel` and `CLOUDFLARE_TUNNEL_TOKEN` set |

## First users

1. Business admin (moderation, sites, API keys): open `/create-admin-user`.
2. Payload admin (content at `/admin`): open `/admin` and create the first user there.
3. Create a site in `/moderation` and add the page's exact origin. A missing origin produces `403 ORIGIN_NOT_ALLOWED`.

## Turnstile

Turnstile is a hosted Cloudflare service, not a container. The Compose defaults are Cloudflare's public testing keys:

```bash
TURNSTILE_SITE_KEY=1x00000000000000000000AA
TURNSTILE_SECRET_KEY=1x0000000000000000000000000000000AA
```

They always pass and work on any hostname, including localhost. For production, create a Turnstile widget in Cloudflare, set the real site key and secret in `.env`, and add every embedding hostname to the widget's allowed hostnames. Signed-in comments skip verification; guest comments fail closed if the secret is missing or Siteverify is unreachable.

## Data and backups

PostgreSQL 18 stores its cluster below `/var/lib/postgresql`; the Compose volume is named `last-comments-pgdata`. Normal restarts and `docker compose down` keep it. `docker compose down -v` deletes it.

```bash
# Payload database
docker compose exec -T postgres pg_dump -U demo -d template_demo > template_demo.sql
# Business comments/auth database
docker compose exec -T postgres pg_dump -U business -d business_comments > business_comments.sql
```

Restore into a fresh volume with `psql` in the `postgres` service, then restart `app` and `worker`. A PostgreSQL major-version upgrade needs a dump/restore or `pg_upgrade`; changing only the image tag does not migrate the cluster.

## Production checklist

- Set `NODE_ENV=production`, `PAYLOAD_PUBLIC_SERVER_URL=https://comments.example.com`, and `BETTER_AUTH_URL` to the same public origin.
- Replace `PAYLOAD_SECRET`, `BETTER_AUTH_SECRET`, `POSTGRES_PASSWORD` and `BUSINESS_DB_PASSWORD`; update the URLs in `.env` to match.
- Put a TLS reverse proxy in front of port 3000 and overwrite `x-real-ip`. The rate-limit plugin trusts that header; without a trusted proxy, guests can spoof their rate-limit identity.
- Use real Turnstile keys and register the embedding origins in Cloudflare.
- Run exactly one `worker` replica for the outbox, and run the `migrate` service once per release.
- Back up both databases before upgrading. Keep the volume outside the container lifecycle.

## Continuous deployment (GitHub Actions)

`.github/workflows/cd.yml` deploys every green `ci` run on `main`, and can be dispatched by hand to re-deploy the current commit. The runner joins the tailnet with a Tailscale OAuth client, then SSHes to the host — production exposes no public SSH port.

Each deploy:

1. clones `https://github.com/lst97-oss/last-comments.git` into `~/last-comments/production` on the first run, then checks out the deployed commit;
2. rewrites `~/last-comments/production/.env` from the GitHub `production` environment;
3. logs in to GHCR, pulls `ghcr.io/lst97-oss/last-comments:<commit>`, and runs `docker compose --profile tunnel up -d`;
4. waits for `/api/ready`, then checks `https://last-comments.lst97.dev/`.

The image is built and pushed by the `docker` job in `ci.yml`, tagged with the commit SHA and `latest`. Nothing on the host is hand-edited: the checkout and `.env` are regenerated from the repository and the environment on every deploy.

### GitHub `production` environment

Secrets:

| Secret | Purpose |
| --- | --- |
| `TAILSCALE_OAUTH_CLIENT_ID` | Tailscale OAuth client; needs the `auth_keys` write scope and `tag:ci` in its tag list |
| `TAILSCALE_OAUTH_CLIENT_SECRET` | OAuth client secret |
| `SSH_KEY_B64` | base64 of the private key whose public half is in the host's `authorized_keys` |
| `PAYLOAD_SECRET` | Payload secret, 32+ characters |
| `BETTER_AUTH_SECRET` | better-auth secret, 32+ characters |
| `POSTGRES_PASSWORD` | Compose Postgres password for the `demo` user |
| `BUSINESS_DB_PASSWORD` | Compose Postgres password for the `business` user |
| `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY` | Real Turnstile widget; the testing keys pass but verify nothing |
| `CLOUDFLARE_TUNNEL_TOKEN` | Token for the `tunnel` profile |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Optional; set both or neither |
| `BLOG_SITE_KEY`, `BLOG_PUBLISHER_API_KEY` | Optional; enables the blog comment widget |
| `OPENROUTER_API_KEY` | Optional; filter plugin |
| `GHCR_TOKEN` | Optional PAT with `read:packages`; defaults to `GITHUB_TOKEN` |

Variables: `TAILSCALE_HOST` (the host's tailnet address, e.g. `100.102.247.97`), `SSH_USER` (defaults to `lst97`), `APP_PORT` (defaults to `3000`).

### DNS and the tunnel

`last-comments.lst97.dev` needs a proxied `CNAME` to `<tunnel-uuid>.cfargotunnel.com` in Cloudflare, and that tunnel's public hostname must route to `http://app:3000` (the Compose service) or `http://localhost:3000`. Until the name resolves, the deploy's final check logs a notice and skips.

## Cloudflare Tunnel

`cloudflared` runs on the same host — the bundled `tunnel` service, or a separate install — and reaches the app over `http://app:3000` (Compose network) or `http://localhost:3000`. Either peer is a private or loopback address, trusted by default, so `RATE_LIMIT_TRUSTED_PROXY_CIDR` can stay unset. Run the tunnel on another host and the peer is that host's address: list it (`RATE_LIMIT_TRUSTED_PROXY_CIDR=203.0.113.10/32`), or every guest shares one rate-limit bucket.

Cloudflare sends `CF-Connecting-IP` (the visitor IP) and `X-Forwarded-For`, but never `X-Real-IP` — the rate-limit plugin reads `CF-Connecting-IP` first, so a tunnel needs no extra header setup and every visitor gets their own bucket (the Cloudflare header wins over an `X-Real-IP` some intermediary injected with the address it saw). If Cloudflare's **Remove visitor IP headers** transform is on, no visitor IP reaches the origin and the tunnel's address becomes the identity again; leave that transform off for this hostname.

## Upgrades

```bash
docker compose pull postgres
docker compose build --pull app
docker compose up -d
```

The `migrate` service runs before the app starts. Rebuild after changing dependencies or source. If a migration fails, `docker compose logs migrate` shows the error and the app does not start.
